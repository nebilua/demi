Project: "Second Brain" — an open-source, local-first personal assistant app for Android.

CORE PRINCIPLES (non-negotiable):
- Fully open source, every component and dependency.
- Runs entirely locally by default, including on low-end Android phones (2–4GB RAM).
- Cloud/network use is opt-in fallback only, never a requirement.
- Priority order of features: (1) personalization/learning system, (2) natural
  conversation, (3) calendar + todo management. Booking automation and phone-call
  integration are explicitly OUT of scope for now.

MVP SCOPE:
1. Natural back-and-forth chat, powered by a local LLM.
2. Calendar with reminders (read/write Android's native Calendar Provider + AlarmManager).
3. A todo list (build custom/local — do NOT integrate a proprietary service like Todoist).
4. Three-tier, user-configurable inference fallback:
   - Tier 0: on-device LLM (default, always tried first)
   - Tier 1: optional home-server LLM over local network/Tailscale (e.g. Ollama)
   - Tier 2: optional cloud API fallback (OpenRouter — provider-agnostic, user supplies key)
5. A genuine personalization/memory system (see below) — this is the app's main
   differentiator and should drive architecture decisions.

PERSONALIZATION / MEMORY SYSTEM (most important part):
Three layers:
1. Episodic memory — raw timestamped log of every conversation turn (SQLite).
2. Semantic facts — durable, distilled facts about the user (preferences, routines,
   relationships, traits), extracted periodically from batches of recent conversations
   via a background job (Android WorkManager, run on idle/charging — NOT live per-message).
   Deduplicate/merge using embedding similarity (e.g. MiniLM via ONNX Runtime Mobile).
3. Working profile — a compact (~300–800 token) natural-language summary rebuilt
   periodically from the fact store, injected into every chat system prompt.
Include a light confirmation loop: when a new inferred fact has low confidence, the
assistant should occasionally ask the user to confirm it rather than assume silently.

TECH STACK (all open source):
- Android app: Kotlin, Jetpack Compose UI
- Local DB: Room (SQLite)
- Background jobs: WorkManager
- On-device inference: llama.cpp compiled via NDK/JNI, running small quantized GGUF
  models (e.g. Qwen2.5-1.5B/3B-Instruct, Q4_K_M)
- Home-server fallback: Ollama, reached over LAN or Tailscale
- Cloud fallback: OpenRouter API (single key, provider-agnostic)
- Speech (later phase): Vosk for offline STT, Piper for offline TTS
- Embeddings (later phase): all-MiniLM-L6-v2 via ONNX Runtime Mobile, for fact dedup
  and semantic recall

DATA SCHEMA (Room entities):
- conversation(id, timestamp, role, content)
- fact(id, text, category[preference|routine|relationship|trait], confidence 0–1,
  sourceConvId, createdAt, lastConfirmedAt, embedding)
- todo(id, text, dueDate, priority, tags, done, createdAt)
- profile_summary(id [singleton row], summaryText, lastRebuiltAt)
- Calendar events are NOT a custom table — read/write directly against Android's
  native Calendar Provider.

PROMPT TEMPLATES TO USE:
1. Main chat system prompt: injects the working profile summary + todos due soon,
   instructs the model to use them naturally without mentioning it's "referencing notes."
2. Fact-extraction prompt (background job): given a batch of recent conversations and
   existing facts, extract only durable, non-time-bound facts, output as
   "CATEGORY | FACT TEXT | CONFIDENCE" lines.
3. Profile-rebuild prompt (run weekly, can use a bigger fallback-tier model): synthesize
   all stored facts into a flowing, non-bulleted natural-language profile under 500 words.

PHASED BUILD ORDER:
Phase 1 — Local LLM + basic chat UI + conversation logging, no personalization/fallback yet.
Phase 2 — Fallback tiers: home-server + cloud API, with settings toggle and escalation logic.
Phase 3 — Todo list CRUD + Calendar/reminders integration, with simple model tool-calling
           (e.g. model outputs "ADD_TODO: text | date", app parses and executes it).
Phase 4 — Voice in/out via Vosk + Piper.
Phase 5 — Full personalization pipeline: background fact extraction, embedding dedup,
           profile rebuild job, confidence-based confirmation loop.
Phase 6 — Polish: settings to control tiering behavior, a screen to review/edit stored
           facts (user should always be able to see/edit what's been learned about them),
           battery/performance tuning.

INSTRUCTION: Start with Phase 1 only. Confirm it's fully working before proposing Phase 2.
